# 작업 유형 플레이북

## planning

- 문제, 범위, 우선순위, 성공 기준을 먼저 정리한다.
- 불확실한 요구사항은 확인 질문으로 남긴다.
- 완료 결과는 CEO가 다음 작업을 배정할 수 있는 수준이어야 한다.

## research

- 확인된 사실과 추정을 분리한다.
- 최신성이나 정확도가 중요한 내용은 공식 출처나 직접 확인 가능한 근거를 우선한다.
- 접근 권한, 비용, 인증이 필요하면 `blocked`로 끝낸다.

## design

- 사용자 흐름, 화면 구조, 상호작용, 접근성을 함께 다룬다.
- 기존 디자인 시스템과 화면 패턴을 먼저 확인한다.
- 텍스트, 버튼, 상태가 모바일과 데스크톱에서 겹치지 않게 고려한다.

## architecture

- 현재 코드 구조와 호출부를 읽은 뒤 권장 구조를 제안한다.
- 데이터 흐름, 공개 인터페이스, 저장소 영향을 분리한다.
- 큰 방향 전환이나 호환성 파괴는 승인 필요 항목으로 남긴다.

## implementation

- 작업 범위에 필요한 파일만 수정한다.
- 관련 테스트, 타입체크, 빌드, 또는 최소 검증을 실행한다.
- 실패한 검증은 실제 오류를 읽고 결과에 남긴다.

## qa

- 기능, 회귀, 오류 상태, 접근성 관점을 분리한다.
- UI나 브라우저 대상이 있으면 기존 Codex Browser 또는 사용 가능한 브라우저 도구로 확인한다.
- 브라우저 도구, URL, 실행 방법, 인증이 없으면 `blocked`로 끝내고 `needs`에 필요한 정보를 적는다.

## release

- 실제 배포를 실행하지 않는다.
- 릴리즈 노트, 배포 전 체크리스트, 롤백 방법, 승인 필요 항목을 산출한다.
- 배포, push, 외부 공개, 비용 발생, 인증 변경은 사용자 승인 없이는 하지 않는다.

## knowledge

- 결정사항, 근거, 열린 질문, 다음 액션을 분리한다.
- 다음 세션이 이어받을 수 있는 최소 맥락을 남긴다.
- 민감 정보나 인증 정보는 기록하지 않는다.

## general

- 역할 문서와 작업 파일의 지시를 우선한다.
- 불확실한 경우 완료 대신 `blocked`로 끝내고 필요한 정보를 `needs`에 적는다.
- `done.json`과 `result.md` 완료 계약을 반드시 지킨다.
