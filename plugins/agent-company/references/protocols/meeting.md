# 회의 프로토콜

## 기본 원칙

1. CEO가 사용자 목표를 한 문장으로 정리한다.
2. CEO가 회의 목적, 필요한 역할, 제외할 역할, 기대 산출물을 정한다.
3. CEO가 필요한 직원에게만 좁고 검증 가능한 검토를 맡긴다.
4. 중요 판단이면 소유 역할과 협업 역할에게 각각 짧은 서면 검토를 맡긴다.
5. 단순하거나 좁은 판단이면 `record_meeting`만 남기고 바로 실행 계획으로 넘어갈 수 있다.
6. CEO는 결정 독점자가 아니라 회의 진행자와 최종 보고자다. 직원 합의가 분명하면 합의를 우선 보고하고, 이견이 있으면 근거와 권장안을 분리해 보고한다.

## 역할 검토 흐름

1. CEO는 `delegation-routing.md`를 기준으로 소유 역할 하나와 필요한 협업 역할만 고른다.
2. 각 역할에는 자기 책임 범위의 질문과 기대 산출물만 맡긴다.
3. CEO는 결과를 모아 합의점, 이견, 부족한 근거, 다음 액션을 정리한다.
4. 여러 역할 결과가 뒤섞여 재개 맥락이 필요하면 기록·지식관리 담당자에게 요약을 맡긴다.
5. 의미 있는 결정은 `record_meeting`과 `record_decision`으로 남긴다.

## 직원 직접 메시지

직원은 좁은 질문, 근거 요청, 리스크 확인이 필요할 때 `companyctl peer-message` 또는 `send_peer_message`로 다른 직원에게 직접 메시지를 보낼 수 있다. 직접 메시지는 `.agent-company/messages/`와 대상 직원 inbox에 파일로 남고, tmux 알림으로 전달된다.

직접 메시지는 작업 배정이나 승인 우회 수단이 아니다. 배포, 삭제, 비용 발생, 인증 변경, 큰 방향 전환은 CEO가 사용자 승인을 받아야 한다.

## 참여자 선택 기준

- 제품 범위와 우선순위가 핵심이면 서비스 기획자를 부른다.
- 외부 사실, 경쟁 제품, 기술 비교 근거가 필요하면 리서치 담당자를 부른다.
- 사용자 흐름, 화면 구조, 카피, 접근성이 핵심이면 UI/UX 디자이너를 부른다.
- 모듈 경계, 데이터 흐름, 확장성, 기술 리스크가 핵심이면 프로젝트 아키텍트를 부른다.
- 구현 범위가 명확하고 코드 변경이 필요하면 풀스택 개발자를 부른다.
- 회귀 위험, 테스트 전략, 품질 기준이 핵심이면 QA 엔지니어를 부른다.
- 배포, 롤백, 릴리즈 노트가 필요하면 릴리즈 담당자를 부른다.
- 회의가 둘 이상의 역할을 포함하면 기록·지식관리 담당자에게 정리를 맡기거나 `record_meeting`으로 직접 남긴다.

## 실행 전환

CEO는 검토 결과를 칸반 작업으로 쪼개고 담당자를 배정한다. 개발자는 구현하고 QA는 필요할 때 검증한다. 릴리즈 담당자는 출시 판단이 필요할 때만 배포 준비 상태를 정리한다.

## 회의 원칙

각 직원에게는 좁고 검증 가능한 작업을 준다. CEO는 긴 논쟁을 방치하지 않고, 직접 메시지와 역할별 검토 결과를 모아 합의점, 이견, 남은 질문으로 정리한다. 전체 직원 회의는 큰 방향 전환이나 여러 분야 리스크가 동시에 얽힌 경우에만 사용한다.
