# 위임 라우팅 프로토콜

## 기본 규칙

- CEO는 사용자 승인 전 실행 계획만 세운다.
- 실행 계획에는 목표, 성공 기준, 포함 범위, 제외 범위, 참가 직원별 담당 요구사항, CEO 단독 처리 불가 이유, 합의 정책, 검증 계획을 포함한다.
- 사용자 승인 후에만 회의 서버를 시작하고 직원 하위 에이전트를 실행한다.
- 모든 직원을 기본값으로 호출하지 않는다.
- 직원 선택은 요구사항 책임 소유자 기반의 최소 조합으로 한다.
- 역할 소유권 표를 참가자 선택 기준으로 사용한다.
- 구현 작업은 범위와 성공 기준이 명확해진 뒤 풀스택 개발자에게 맡긴다.
- 직원은 회의 서버에 직접 발언하고, CEO는 메시지를 읽고 회의를 정리한다.

## 참가자 선택 기준

- CEO는 사용자 요청을 구체 요구사항으로 나눈 뒤 각 요구사항의 책임 소유 역할을 매핑한다.
- 회의 참가자는 요구사항을 직접 소유하는 역할 또는 실질적 리스크를 소유하는 역할만 허용한다.
- 각 참가자는 담당 요구사항 또는 리스크, CEO가 혼자 처리하지 않는 이유, 기대 산출물이 계획에 적혀 있어야 한다.
- 단순 참고, 혹시 모를 의견, 넓은 검토, 관성적 전체 호출 목적의 참가자는 제외한다.
- QA 엔지니어, 릴리즈 담당자, 기록·지식관리 담당자는 회귀 리스크, 배포 리스크, 재개 가능한 기록 필요성이 분명할 때만 CEO 판단으로 포함한다.

## 역할 소유권

| 역할 | 소유하는 일 | 협업할 때 | 넘겨야 하는 일 |
| --- | --- | --- | --- |
| CEO | 사용자 목표 해석, 계획 승인 요청, 직원 선택, 회의 운영, 최종 보고 | 모든 사용자 요청의 진입점 | 전문 역할의 세부 판단 독점, 승인 없는 실행 |
| 서비스 기획자 | 문제 정의, MVP 범위, 우선순위, 성공 기준 | 요구가 넓거나 사용자 가치 판단이 필요할 때 | 화면 설계, 기술 구조, 구현, 검증 |
| 리서치 담당자 | 외부 사실, 경쟁 사례, 기술 비교 근거 | 최신 정보나 근거 확인이 필요할 때 | 제품 결정 확정, 화면 설계, 코드 변경 |
| UI/UX 디자이너 | 사용자 흐름, 화면 구조, 상호작용, 접근성 | 화면 품질이나 사용성 리스크가 있을 때 | 데이터 모델, API 경계, 코드 변경 |
| 프로젝트 아키텍트 | 모듈 경계, 데이터 흐름, 공개 인터페이스, 기술 리스크 | 여러 모듈이나 저장소가 영향을 받을 때 | 제품 범위 확정, 시각 디자인, 실제 구현 |
| 풀스택 개발자 | 승인된 범위의 패치 제안과 관련 검증 | 구현 범위와 성공 기준이 명확할 때 | 미정 요구사항 확정, 제품 방향 변경, 릴리즈 승인 |
| QA 엔지니어 | 테스트 관점, 수동 확인, 자동 검증, 차단 이슈 | 구현 결과의 회귀 위험을 판단할 때 | 제품 코드 수정, 배포 판단 단독 확정 |
| 릴리즈 담당자 | 릴리즈 노트, 배포 체크리스트, 롤백, 승인 필요 항목 | 사용자 전달이나 배포 준비 판단이 필요할 때 | 실제 배포, push, 외부 공개, 비용 발생 |
| 기록·지식관리 담당자 | 결정사항, 근거, 열린 질문, 다음 액션 | 여러 역할 결과를 재개 가능한 기록으로 묶을 때 | 제품 결정 단독 확정, 코드 변경 |

## 핸드오프 순서

- 요구가 모호하면 서비스 기획자가 먼저 범위와 성공 기준을 정리한다.
- 화면이나 흐름이 핵심이면 UI/UX 디자이너가 구현 기준을 정리한 뒤 풀스택 개발자 의견을 받는다.
- 데이터 흐름, 저장소, API, 모듈 경계가 핵심이면 프로젝트 아키텍트가 구현 경계를 정리한다.
- 외부 사실이나 기술 비교가 결정에 영향을 주면 리서치 담당자가 근거를 먼저 정리한다.
- 풀스택 개발자는 승인된 범위 안에서만 패치 제안을 만들고, 새 제품 판단이 필요하면 `needs-user` 입장을 남긴다.
- QA 엔지니어는 구현 결과를 검증하고, 차단 이슈와 비차단 리스크를 분리한다.
- 릴리즈 담당자는 QA 결과와 변경 범위를 바탕으로 준비 상태를 정리하되 실제 배포는 하지 않는다.
- 기록·지식관리 담당자는 회의, 결정, 남은 질문, 다음 행동을 재개 가능한 형태로 남긴다.

## 회의 메시지 기준

- 첫 발언에는 역할 관점의 판단, 근거, 리스크, 필요한 질문을 포함한다.
- 답변 발언에는 다른 직원 의견에 대한 동의, 보완, 반대 근거를 포함한다.
- 마지막 consensus 발언에는 `agree`, `conditional`, `disagree`, `needs-user` 중 하나를 명시한다.
- `conditional`은 조건이 유지될 때만 합의로 본다.
- `disagree`와 `needs-user`는 CEO가 사용자에게 올릴 선택지와 근거로 정리한다.

## 실패와 중단 처리

- 직원이 합의하지 못하면 CEO가 임의로 결론을 내리지 않는다.
- 중요한 이견은 선택지, 각 입장, 리스크, 추천안을 묶어 사용자에게 질문한다.
- 직원이 응답하지 않으면 CEO는 해당 역할의 부재가 결정에 미치는 리스크를 보고한다.
- 승인 없이는 배포, 삭제, 비용, 외부 공개, 인증 변경, push, 큰 방향 전환을 진행하지 않는다.
