# 위임 라우팅 프로토콜

## 기본 규칙

- CEO는 작업을 시작하기 전에 작업 유형, 소유 역할, 협업 역할, 제외 역할, 기대 산출물을 정한다.
- `delegate_task`는 산출물을 책임지는 소유 역할에게만 보낸다.
- 전체 직원 회의는 여러 분야의 리스크가 동시에 얽힌 중요한 판단에만 사용한다.
- 구현 작업은 범위, 성공 기준, 필요한 설계 결정이 정리된 뒤 풀스택 개발자에게 맡긴다.
- 코드가 바뀐 뒤 회귀 위험이 있으면 QA 엔지니어에게 검증을 맡긴다.
- 둘 이상의 역할 결과가 의사결정에 쓰이면 기록·지식관리 담당자 또는 `record_meeting`으로 결정과 근거를 남긴다.

## 역할 소유권

| 역할 | 소유하는 일 | 협업할 때 | 넘겨야 하는 일 |
| --- | --- | --- | --- |
| CEO | 사용자 목표 해석, 프로세스 설계, 역할 위임, 결과 취합, 최종 보고 | 모든 사용자 요청의 진입점 | 각 전문 역할의 실제 산출물 작성, 제품 코드 직접 수정 |
| 서비스 기획자 | 문제 정의, MVP 범위, 우선순위, 성공 기준 | 요구가 넓거나 사용자 가치 판단이 필요할 때 | 화면 설계, 기술 구조, 구현, 검증 |
| 리서치 담당자 | 외부 사실, 경쟁 사례, 기술 비교 근거 | 최신 정보나 근거 확인이 필요할 때 | 제품 결정 확정, 화면 설계, 코드 변경 |
| UI/UX 디자이너 | 사용자 흐름, 화면 구조, 상호작용, 접근성 | 화면 품질이나 사용성 리스크가 있을 때 | 데이터 모델, API 경계, 코드 변경 |
| 프로젝트 아키텍트 | 모듈 경계, 데이터 흐름, 공개 인터페이스, 기술 리스크 | 여러 모듈이나 저장소가 영향을 받을 때 | 제품 범위 확정, 시각 디자인, 실제 구현 |
| 풀스택 개발자 | 승인된 범위의 코드 변경과 관련 검증 | 구현 범위와 성공 기준이 명확할 때 | 미정 요구사항 확정, 제품 방향 변경, 릴리즈 승인 |
| QA 엔지니어 | 테스트 관점, 수동 확인, 자동 검증, 차단 이슈 | 구현 결과의 회귀 위험을 판단할 때 | 제품 코드 수정, 배포 판단 단독 확정 |
| 릴리즈 담당자 | 릴리즈 노트, 배포 체크리스트, 롤백, 승인 필요 항목 | 사용자 전달이나 배포 준비 판단이 필요할 때 | 실제 배포, push, 외부 공개, 비용 발생 |
| 기록·지식관리 담당자 | 결정사항, 근거, 열린 질문, 다음 액션 | 여러 역할 결과를 재개 가능한 기록으로 묶을 때 | 제품 결정 단독 확정, 코드 변경 |

## 핸드오프 순서

- 요구가 모호하면 서비스 기획자가 먼저 범위와 성공 기준을 정리한다.
- 화면이나 흐름이 핵심이면 UI/UX 디자이너가 구현 기준을 정리한 뒤 풀스택 개발자에게 넘긴다.
- 데이터 흐름, 저장소, API, 모듈 경계가 핵심이면 프로젝트 아키텍트가 구현 경계를 정리한 뒤 풀스택 개발자에게 넘긴다.
- 외부 사실이나 기술 비교가 결정에 영향을 주면 리서치 담당자가 근거를 먼저 정리한다.
- 풀스택 개발자는 넘겨받은 범위 안에서만 구현하고, 새 제품 판단이 필요하면 `blocked`로 끝낸다.
- QA 엔지니어는 구현 결과를 검증하고, 차단 이슈와 비차단 리스크를 분리한다.
- 릴리즈 담당자는 QA 결과와 변경 범위를 바탕으로 준비 상태를 정리하되 실제 배포는 하지 않는다.
- 기록·지식관리 담당자는 회의, 결정, 남은 질문, 다음 행동을 재개 가능한 형태로 남긴다.

## 작업 파일 기준

- 지시문에는 사용자 목표, 소유 역할의 책임, 제외 범위, 기대 산출물, 완료 기준을 포함한다.
- 구현 작업에는 상위 결정 출처와 검증 가능한 성공 기준을 포함한다.
- QA 작업에는 실행 방법, 확인 대상, 자동 검증 후보, 수동 확인 범위를 포함한다.
- 릴리즈 작업에는 변경 묶음, 검증 결과, 승인 필요 행동, 롤백 기대치를 포함한다.

## 실패와 타임아웃 처리

- 기획, 리서치, 디자인, QA, 릴리즈, 기록 작업의 `wait_for_task`는 짧고 명확한 시간으로 사용할 수 있고, 실패나 시간 초과가 나면 그 상태를 기록한다.
- 풀스택 구현 작업에는 짧은 `wait_for_task` 시간을 실패 신호로 쓰지 않는다. 구현은 오래 걸릴 수 있으므로 긴 대기 시간이나 반복적인 `task_status` 확인을 사용하고, `done.json` 또는 명시적인 `blocked` 결과가 나올 때까지 기다리는 것을 기본값으로 삼는다.
- 구현 작업이 느리면 바로 CEO가 직접 구현하거나 다른 역할로 넘기지 않는다. 먼저 `task_status`로 산출물 상태를 확인하고, 진행 상황과 대기 방침을 사용자에게 보고한다.
- 실패한 역할을 무한히 기다리지 않는다.
- CEO는 실패 원인을 읽은 뒤 같은 역할에 더 좁게 재위임하거나, 다른 소유 역할로 넘기거나, 사용자 승인이 필요한 항목으로 올린다.
- 타임아웃이나 실패를 숨기지 않고 최종 보고에 포함한다.
